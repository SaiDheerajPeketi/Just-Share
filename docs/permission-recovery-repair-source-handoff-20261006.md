## Three reviewed blockers and targeted repair

1. **Progress remained active after permission revocation.** Progress previously stopped a transport but retained the shared `hasTransferStarted`/percentage, allowing the green active marker and Transferring caption to remain. `TransferViewModel.markPermissionInterrupted` now invalidates the current Wi-Fi progress generation, marks an unfinished active transfer interrupted, clears its started flag, and retains its URIs, direction, method, file metadata and current file information. Completed results remain complete while queued old updates are invalidated. Existing reset/start paths clear the new in-memory interruption flag. The actual progress permission effect calls this state transition before transport cleanup; the actual summary renders an interrupted caption, a stopped marker and recovery copy. Its active color/indicator also excludes failure. Go Back retains the existing clear-progress/back-to-discovery recovery path. Bluetooth completion derived by the screen is passed into the state transition so completed Bluetooth results are not labelled interrupted.

2. **A retained ACTION_FOUND callback could read protected metadata after revocation.** The actual controller routes its lazy device name/class/address read through `handleFoundDevice`. The handler checks active receiver registration and actual CONNECT/local grants immediately before that read, and catches SecurityException from a getter revocation race. Denied/racing callbacks stop discovery; stop and close unregister the found receiver before checking the scan cancellation grant, allowing revoke cleanup even when SCAN is already unavailable. An inactive callback cannot read or publish metadata, and a later allowed scan can register once again. The activity flag is volatile for visibility when connection cleanup occurs on another thread. The adjacent bonded-device metadata read has the same SecurityException race handling. Accepted names/classes, deduplication, cold connection flows and transfer protocol remain unchanged.

3. **Discovery and progress previously owned different Wi-Fi ViewModels.** The graph now captures its host ViewModelStoreOwner before NavHost replaces local owners per destination. Both discovery routes resolve the Wi-Fi ViewModel against that explicit owner inside allowed discovery content, and progress receives the same owner-resolved instance. Hilt remains the production factory; the resolver accepts an AndroidX factory solely for source regression fixtures. Thus progress revocation operates on the actual discovery transport rather than a new idle per-entry owner. `WifiLocalTransferLifetime` opens a permission-checked lease before Wi-Fi discovery content, retains it across discovery/progress/retry, and releases it when leaving for Home or another nonlocal destination. Release requires the captured lease identity, so delayed disposal cannot stop a replacement. Wi-Fi progress may render an idle instance to show recovery without initializing a channel. No navigation architecture, provider, schema or dependency was introduced.

   The ViewModel starts closed, preserves role across cleanup, cancels connection/hosting/discovery/refresh/timeout/delayed-restart/stop jobs, unregisters its receiver, stops the existing service directly, and nulls its channel/manager (calling Channel.close on API 27+, as supported by the existing platform boundary). Allowed re-entry opens a fresh lease; discovery initializes a fresh channel and registers again. The discovery effect also rechecks actual Wi-Fi grants immediately before manager initialization. Replacing an existing channel cancels channel-bound jobs and closes the prior channel on API 27+. Registered broadcasts are bound to both receiver identity and lease; old connection/group/peer request callbacks are bound to lease and channel, and delayed restart checks the same identity. Initial sticky connection broadcasts remain ignored; initialization still adopts only an already-formed group, preserving receiver hosting startup. Framework callbacks after normal exit remain inactive even when grants are still allowed. Receiver/service reentry is covered by declared fake-boundary regressions; real channel and radio behavior and job cancellation remain source-inspected, unexecuted.

The global Bluetooth ViewModel remains eagerly created by the existing graph parameter; its initial setup is guarded/idle and no new discovery start is claimed. Wi-Fi construction is delayed behind the selected discovery gate on those routes; a direct progress entry can resolve an idle host instance, whose initialization/service entry is still permission-guarded. This repair does not claim that every ViewModel is created after a gate.
